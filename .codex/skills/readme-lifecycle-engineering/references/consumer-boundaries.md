# Consumer authority and documentation boundaries

Read the target repository's current instructions, project state, adopted decisions,
build manifests and evidence before describing it. The skill supplies a documentation
method and does not choose a product stack, canonical configuration, protocol,
storage engine, support matrix, license or publication policy.

Distinguish implemented, observed, planned and unknown capabilities. A complete
product vision does not establish a working release; a small implemented slice does
not redefine the product's intended scope. Read current source and feature evidence
before documenting commands, performance, screenshots or support promises.

Keep one canonical location for each policy, contract and task explanation. Link
README entry paths to it rather than copying instructions into every package. Add
package READMEs only for actual independent reader entry points; a suggested tree
never authorizes new product directories or an application redesign.

In an SDD consumer, use its existing requirements, decisions, tasks and evidence
vocabulary; do not require SDD in a consumer that does not use it. AGENTS instructions
and skills do not grant command execution, network, installation or publication.
Documentation updates inherit the user's actual authorized scope.

The supplied package's Ec-specific examples and research ledger remain provenance,
not transferable product rules. For Ox, consult its root AGENTS and linked project,
constitution and architecture authorities; keep application and governance commands
and their acceptance boundaries distinct. Re-read those sources when they change.
